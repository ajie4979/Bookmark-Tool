## 0. 文档说明与设计立场

### 0.1 这是一份全新设计

本设计**不从属于任何既有开源项目**。

设计过程中参考过一个一年前的 Chrome 扩展（bookmark-sage 1.0.0），但仅仅参考了它的
**产品思路**（用 AI 给书签推荐目录）。本设计在以下方面与它**没有任何继承关系**：

| 维度 | 参考项目 | 本设计 |
|------|---------|--------|
| 形态 | Chrome 扩展 | Windows 桌面应用 |
| 语言 | JavaScript | Python |
| 架构 | 浏览器插件 + content script | 分层桌面应用（core / ui 分离） |
| 数据对象 | 直连浏览器书签树 | 书签文件（显式快照，可回滚） |
| 核心能力 | AI 分类（单一） | 去重 / 验证 / 归类 / 导航页 / 导入导出（六项） |
| 代码 | — | **零复制**，全部重新实现 |

因此本文档中涉及的技术决策、架构与交互，均为针对当前目标重新推导的结果，
不受参考项目的历史包袱约束。

### 0.2 设计驱动力

本文档的核心设计目标来自**实测反馈**，而非凭空设想：

| 实测问题 | 本设计的应对 |
|---------|-------------|
| 网站明明能打开，却被判失效 | 极简三态：任何"服务器活着"的信号（含 403、含 TLS 报错、含 5xx）一律判「可访问」，只有页面真没了/域名没了才判「已失效」（第 5 章） |
| 不开 VPN 打不开，开了能开 | 网络出口（Exit Profile）概念 + 复检机制 |
| 开了 VPN 反而打不开 | 乐观合并：任一出口能通即判可访问 |
| 分类结果与实际不符 | 双引擎 + 人工修正 + 反馈沉淀（第 6 章） |

**一句话概括设计哲学：宁可说"我不知道"，也不要硬判"它坏了"。**

## 1. 产品定义

### 1.1 一句话描述

一个离线的 Windows 桌面工具，把浏览器导出的书签文件，清洗成一份可信、有序、
可检索、可回灌浏览器的资产。

### 1.2 目标用户

- **重度收藏者**：书签积累三五年，目录结构早已失控，失效链接成堆
- **迁移用户**：换电脑/换浏览器，希望先清洗再导入，不带垃圾过去
- **知识工作者**：想把散落的收藏沉淀成一份可检索的导航页，作为个人知识入口

### 1.3 核心价值（按重要性排序）

1. **可信** —— 判定结果经得起人工复核，不确定就明说
2. **无损** —— 全过程可逆，任何操作都不直接删除数据
3. **离线** —— 除 AI 归类外，不依赖任何外部服务
4. **闭环** —— 清洗完能直接导回浏览器，形成完整回路

### 1.4 非目标

- 不做浏览器插件（不直连浏览器书签，避免程序 bug 损坏用户数据）
- 不做云同步 / 多端（保持单机离线的确定性与隐私性）
- 不做书签内容抓取与全文检索（范围太大，与定位不符）

### 1.5 命名

| 字段 | 值 |
|------|----|
| 中文名 | **书签医生** |
| 英文名 | **Bookmark Doctor** |
| 项目内部名 | bookmark-doctor |
| 应用 ID | Bookmark Doctor |
| 主图标 | 蓝底圆角 + 白色书签 + 蓝色心跳脉冲线（见 `resources/icon.png`） |
| 可执行文件名 | 书签医生.exe |

**命名理由**：核心动作是给书签"体检"（验证可达性）+ "治疗"（去重、归类、导出），
"存疑 / 确诊 / 复检"这套术语与医疗流程天然契合，且好记、有画面感。

**应用图标**：圆角蓝底 #185FA5 + 白色书签轮廓 + 内部蓝色脉冲线。
脉冲线代表"检测链接存活"——也是产品核心能力。多尺寸 .ico 由 `tools/make_icon.py`
4× 超采样后降采样生成，保证 16px 下的边缘质量。

## 2. 术语与数据模型

### 2.1 核心术语

| 术语 | 定义 |
|------|------|
| **书签** | 一条记录：URL + 标题 + 所属路径 |
| **网络出口（Exit Profile）** | 一次验证所走的网络路径：直连 / 系统代理 / 自定义代理 |
| **探测（Probe）** | 在某个出口下，对某 URL 发起的一次完整请求（含降级链） |
| **验证会话（Session）** | 对一批书签、在某个出口下执行的一轮完整验证 |
| **结论（Verdict）** | 综合多次探测后，对某书签可达性的最终判定 |
| **软 404** | HTTP 返回 200，但页面内容实际是"页面不存在" |
| **人工裁定（Override）** | 用户手动下的结论，优先级最高，锁定不被覆盖 |
| **置信度** | 结论的可靠程度：高 / 中 / 低 |

### 2.2 数据模型

```python
@dataclass
class Bookmark:
    # ── 原始字段（导入时确定）──
    id: str                  # 稳定 ID = 归一化 URL 的哈希
    title: str
    url: str
    folder: str              # 原始路径，如 "AI相关/中转站"
    add_date: int
    icon: str = ""           # 默认不加载，省内存

    # ── 去重结果 ──
    norm_url: str
    dup_group: int = -1      # 重复组 ID，-1 表示不重复
    is_primary: bool = True  # 组内是否为保留项
    keep: bool = True        # 是否保留（去重是可逆标记，非删除）

    # ── 验证结果 ──
    verdict: str = "未检测"   # 未检测 / 可访问 / 存疑 / 已失效 / 跳过
    verdict_sub: str = ""     # 子类型：访问受限 / 地区限制 / 软404 / 环境矛盾 ...
    confidence: str = ""      # 高 / 中 / 低
    probes: list = field(default_factory=list)   # 历次探测记录
    override: str = ""        # 人工裁定，非空则覆盖 verdict
    last_checked: int = 0

    # ── 归类结果 ──
    category: str = ""
    category_source: str = ""   # ai / rule / manual
    category_score: float = 0.0

@dataclass
class Probe:
    exit_profile: str        # direct / system / custom:<name>
    session_id: str
    ts: int
    method: str              # 实际成功的方法：HEAD / GET
    status_code: int
    final_url: str           # 重定向后的最终 URL
    soft404: bool = False
    error: str = ""          # 异常类型
    elapsed_ms: int = 0
    public_ip: str = ""      # 该出口的公网 IP（可选）
```

**关键设计：`probes` 保留完整历史而非覆盖。**
这是解决 VPN 场景的基础——同一条书签在直连和代理下的结果可以同时存在，
用户的网络环境变化时，新结果叠加进来，而不是把旧结论冲掉。

│  parser      导入 / 导出（Netscape HTML / JSON / CSV）     │
│  dedupe      去重（并查集分组）                            │
│  prober      可达性验证 ★ 核心                             │
│  classifier  本地规则引擎                                  │
│  ai          OpenAI 兼容客户端                             │
│  rules       用户沉淀的域名规则                            │
│  navgen      导航网页生成                                  │
└────────────────────────┬─────────────────────────────────┘
                         │
┌────────────────────────┴─────────────────────────────────┐
│                      持久化层                              │

│  config.json │ taxonomy.json │ rules.json │ logs\         │
└──────────────────────────────────────────────────────────┘

**分层原则**
- `core` 层不 import 任何 Qt 模块 —— 可独立单元测试、可被 CLI 复用
- UI 层只负责渲染与事件，不含业务逻辑
- 所有耗时任务跑在 QThread，通过信号回传进度

## 5. 验证逻辑（核心）

### 5.1 问题本质

**失效与否不是 URL 的绝对属性，而是「URL × 时刻 × 网络出口」的联合结果。**

同一个 URL 可能出现：

| 场景 | 直连 | 代理 | 真相 |
|------|------|------|------|
| 国内普通站 | ✓ | ✓ | 正常 |
| 被本地网络阻断的站 | ✗ | ✓ | 正常，只是要走代理 |
| 封境外 IP 的站（政府/银行/部分国内站） | ✓ | ✗ | 正常，只是要走直连 |
| 真·关闭的站 | ✗ | ✗ | 确实失效 |

**只在一个网络环境探测一次，必然产生大量假阳性。** 这是本设计要解决的首要问题。

### 5.2 网络出口（Exit Profile）

| 出口标识 | 含义 | 实现 |
|---------|------|------|
| `direct` | 强制直连，忽略系统代理 | `session.trust_env = False` |
| `system` | 跟随系统代理设置 | 默认行为 |
| `custom:<name>` | 用户指定的 HTTP/HTTPS/SOCKS 代理 | `proxies={"http":..., "https":...}` |

**会话开始时可选探测公网出口**：调用 ipinfo.io / myip.com 记录当前出口的
公网 IP 与地理位置，写入 Session 记录。默认**关闭**（隐私考虑），
开启后用户事后能追溯"这批结果是在什么网络下测的"。

### 5.3 单次探测的降级链

一次探测内部按序尝试，任一步成功即停：

```
① HEAD + 完整浏览器请求头
   ├─ 2xx/3xx ──────────────► 进入 ③ 软404检查
   ├─ 404/410 ──────────────► 失败（确定失效，高置信）
   ├─ 403/405/501/400 ──────► 进入 ②
   └─ 网络错误 ─────────────► 进入 ④

② GET + 完整头（stream 模式，只读前 64KB 即断）
   ├─ 2xx/3xx ──────────────► 进入 ③
   └─ 失败 ─────────────────► 进入 ④

③ 软 404 检测（正文前 64KB）
   ├─ 未命中 ───────────────► 成功（可访问）
   └─ 命中 ─────────────────► 存疑（疑似失效）

④ 重试（次数可配，默认 1）
   策略：换 UA（Googlebot / 移动端）或关闭 SSL 校验
   ├─ 成功 ─────────────────► 回到 ③
   └─ 仍失败 ───────────────► 失败（记录错误类型）
```

**为什么 HEAD 优先**：800+ 条书签若全部 GET 下载正文，流量与耗时翻倍。
实际只有少数 HEAD 失败的条目需要降级到 GET。

> ⚠ **实测教训（v2.0 修掉的最大误判源）**
>
> 早期版本只对 400/403/405/501 做 GET 降级，**404 直接判死**。
> 用真实数据（60 条）实测发现，4 条"已失效"里 3 条是误判：
>
> | 站点 | HEAD | GET | 真相 |
> |------|------|-----|------|
> | yige.baidu.com | 404 | **200** | 正常 |
> | chat.baidu.com | 404 | **200** | 正常 |
> | arc.tencent.com/zh/ai-demos/faceRestoration | 404 | **200** | 正常 |
> | 17yongai.com | 404 | 404 | 确实失效 |
>
> 误判率高达 **75%**。根因是很多站点（尤其经过 CDN 的国内站）**没有正确实现
> HEAD**，直接返回 404。
>
> **修正：对所有 4xx/5xx 都用 GET 复核，绝不只凭 HEAD 判死。**
> 修正后同一批数据：已失效 4→1，可访问 47→50，**误判率降到 0**。
> 代价是每条失败链接多一个 GET 请求，完全值得。

**完整浏览器请求头**（降低被 WAF 拦截概率）：
```
User-Agent, Accept, Accept-Language, Accept-Encoding,
sec-ch-ua, sec-ch-ua-mobile, sec-ch-ua-platform,
Sec-Fetch-Dest / Mode / Site / User,
Upgrade-Insecure-Requests, Connection
```

> ⚠ 实测诚实记录：完整头部对 Cloudflare 类 JS 挑战**无效**
> （实测 hum3d.com、clara.io 加头后仍返回 403）。它能改善一部分误判，
> 但不该被当成银弹。这类场景只能靠"存疑 + 人工确认"兜底。

### 5.4 结论判定：极简三态

用户口径：**能打开网页就正常，打不开才不正常**。据此把判定收敛为三态：

```
① 有人工裁定？                          → 采用人工裁定（锁定）
② 任一探测 2xx/3xx（非软404）            → 可访问（高置信）
③ 所有探测均 404/410（页面没了）         → 已失效（高置信）
④ 任一探测收到 HTTP 状态码（含 401/403/429/451/5xx，甚至软404）
                                       → 可访问（中置信）：服务器活着，只是拒绝程序/需浏览器
⑤ 域名彻底没了 / 端口连不上              → 已失效（高置信）
⑥ TLS/证书：服务器回了握手              → 可访问（中置信）：国密/反爬/代理限制，浏览器能开
⑦ 其余（超时 / 无响应 / 其它）           → 存疑（低置信）
```

**核心规则：只要有一丝"服务器活着"的信号（哪怕是 403、哪怕是 TLS 报错），就判可访问。**
只有"页面真没了(404/410)"或"域名/端口没了"才算失效；彻底连不上才留作存疑。

这条规则直接对应用户反馈的两种 VPN 场景——直连失败但代理成功 → 可访问；
代理失败但直连成功 → 同样是可访问。也覆盖了 `12333.gov.cn` 这类 http 跳 https、
被 WAF 拦成 403、或用了国密证书导致 Python 探针 TLS 握手失败、但浏览器能正常打开的站点。

### 5.5 状态词典

| 结论 | 子类型（仅作备注，不改变结论） | 触发 | 算失效 |
|------|--------|------|--------|
| **可访问** | — | 某出口 2xx/3xx | 否 |
| | 环境矛盾 | 不同出口结果不一致（部分 2xx） | 否 |
| | 访问受限 | 401/403/429（反爬/需登录） | 否 |
| | 地区限制 | 451 | 否 |
| | 服务端错误 | 5xx（多半临时，站点在运行） | 否 |
| | 疑似软404 | 200 但内容像"页面不存在" | 否 |
| | TLS限制 | 证书/国密/代理 TLS 限制，浏览器能开 | 否 |
| **已失效** | 页面不存在 | 全部出口 404/410 | 是 |
| | 域名不存在 | DNS 解析失败 | 是 |
| | 无法连接 | 连接被拒 / 不可达 | 是 |
| **存疑** | 网络超时 | 请求超时、完全无响应 | （待人工决定）|
| **未检测** | — | 尚未验证 | 不适用 |
| **跳过** | — | `chrome://` / `javascript:` / 本地文件 | 不适用 |

**子类型不单独成列**（避免状态爆炸），在 tooltip 与筛选器中展示。

> 「可访问」已合并原「站点在线」——只要服务器有任何响应（含被拒、含 TLS 报错），
> 就视为站点活着、可访问；只有确实失效或彻底连不上才另计。这样"存疑"列表只剩
> 真正需要人工抽查的极少条目。

「环境矛盾」是本设计最有价值的信号之一——它明确告诉用户
"这个站点需要特定网络环境"，并可一键沉淀为域名规则。

### 5.6 软 404 检测

```python
SOFT404_PATTERNS = [
    # 中文
    r"页面不存在", r"内容已删除", r"资源已下线", r"找不到该页面",
    r"该页面已被删除", r"您访问的页面",
    # 英文
    r"page not found", r"\b404\b.{0,20}not found",
    r"no longer available", r"this (page|content) (has been )?removed",
    r"couldn'?t find (that|this) page",
]
```

**双重条件**防误判：命中特征词 **且**（正文 < 3KB **或** 标题含 404/not found）。
避免正文里恰好提到"404"就被误杀。

### 5.7 并发与节流

| 参数 | 默认 | 说明 |
|------|------|------|
| 并发线程数 | 32 | 建议 24–48；过高会被目标站限流 |
| 单条超时 | 8s | |
| 失败重试 | 1 | 间隔 0.4s×(n+1) |
| **同域名最小间隔** | 100ms | **关键**：防止对同一站点瞬间打 20 个请求被封 |
| 每线程独立 Session | 是 | thread-local，连接池复用 |

同域名节流实现：按域名分桶，记录上次访问时间，不足间隔则睡眠。

### 5.8 用户规则沉淀

人工裁定或复检结果可一键沉淀为域名规则（`rules.json`）：

```json
{
  "example.com":    {"action": "require_proxy",  "note": "需代理访问", "ts": 1760000000},
  "gov.example.cn": {"action": "require_direct", "note": "封境外 IP"},
  "internal.corp":  {"action": "skip",           "note": "内网地址"}
}
```

下次验证自动生效：

| action | 行为 |
|--------|------|
| `require_proxy` | 只在代理出口检测，该出口成功即判可访问 |
| `require_direct` | 只在直连出口检测 |
| `skip` | 直接跳过，标记"已跳过（用户规则）" |

这让工具**越用越准**：第二次验证的成本与误判率显著下降。

## 6. 分类逻辑

### 6.1 双引擎架构

```
              ┌────────────┐
              │  书签条目   │
              └─────┬──────┘
        ┌───────────┴───────────┐
        │  已配置 AI 且可用？    │
        └──┬────────────────┬───┘
         是│                │否（降级）
           ▼                ▼
     ┌──────────┐     ┌──────────┐
     │ AI 归类  │     │ 规则归类 │
     │ 批量并发 │     │ 打分最高 │
     └────┬─────┘     └────┬─────┘
          │ 未覆盖条目回补  │
          └────────┬───────┘
                   ▼
           ┌──────────────┐
           │ 人工修正     │ ← 表格双击直接改
           │ （优先级最高）│
           └───────┬──────┘
                   ▼
           ┌──────────────┐
           │ 反馈沉淀     │ ← 修正累积后提示加入规则
           └──────────────┘
```

### 6.2 本地规则引擎

打分规则（总分最高者胜）：

| 匹配位置 | 权重 | 备注 |
|---------|------|------|
| 域名命中特征 | +3 | 如 `unrealengine` |
| 标题命中中文关键词 | +2 | 中文子串匹配，歧义小 |
| 标题命中英文关键词 | +3 | **词边界**匹配 |
| 原文件夹命中关键词 | **+1** | 弱信号 |
| URL 路径命中关键词 | +1 | 仅英文且长度 ≥4 |

**两条实测经验（重要）**：

1. **原文件夹权重必须是弱信号（+1 而非 +2）**
   用户自建目录往往很乱。实测中"网站收藏"这个 150 条的杂项文件夹，
   因"网站"二字被"前端与网页"规则命中，一次性误分 102 条。降到 +1 后恢复正常。

2. **短英文关键词必须词边界匹配**
   `ai`、`sd`、`ui` 这类 2–3 字符关键词，子串匹配会让 `mail.qq.com` 命中 `ai`、
   `https` 命中 `sd`。规则：
   - 长度 ≤3：只匹配域名的点分段（`ai` 匹配 `example.ai`，不匹配 `mail.qq.com`）
   - 长度 ≥4：可子串匹配域名与路径
   - 中英混合标题用 `(?<![a-z0-9])kw(?![a-z0-9])` 正则，中文字符天然不构成边界

### 6.3 AI 归类

- **接口**：OpenAI 兼容，地址自动补全 `/v1/chat/completions`
- **输入**：每批 25 条 `{id, title, url, old_folder}`
- **输出**：严格 JSON `{"results":[{"id":n,"category":"...","reason":"..."}]}`
- **解析**：兼容 ```json 围栏、前后废话；用首个 `{` 到末个 `}` 兜底提取
- **并发**：默认 3，可调
- **校验**：返回 category 必须在候选列表内，否则丢弃该条
- **降级**：无 Key / 网络失败 / 解析失败 → 自动回退本地规则，保证流程走完

### 6.4 分类体系

内置 15 个分类 + 其他未分类：

```
AI 与机器学习    3D 与图形创作    设计与素材      开发与技术
前端与网页        数据可视化        智慧城市与GIS    摄影与后期
学习与文档        工具与效率        资讯与社区      影音娱乐
电商与生活        政府与机构        玩机与刷机
```

编辑器支持：增 / 删 / 改名、编辑域名特征与关键词（每行一条）、拖动排序。
改动同时作为 AI 归类的候选分类列表。

### 6.5 反馈闭环

用户手动改分类时记录 `{domain, from_cat, to_cat}`。
当同一域名下累积 ≥5 条相同方向的修正时，提示：

> 检测到您多次把 `example.com` 从「X」改到「Y」，是否加入规则？
> 　　　　　　　　　　　　　　　　　　　[加入] [不再提示]

确认后自动把该域名写入目标分类的 domains 列表。

## 7. 查重逻辑

### 7.1 URL 归一化

```
小写化 scheme 与 host
→ 去掉默认端口（:80 / :443）
→ 去掉认证信息（user:pass@）
→ 剔除追踪参数（utm_* / spm / from / ref / fbclid 等 20+ 种）
→ 去掉 fragment
→ 路径 URL 解码
→ 去掉末尾斜杠
```

**关键决策：归一化保留 http/https 差异。**
协议无关的合并交给"标准"档位的另一套分组键处理——
两个关注点分离，便于单独调节严格度。

### 7.2 三档严格度

| 档位 | 分组键 | 适用 |
|------|--------|------|
| 严格 | 归一化 URL | 只想抓完全一样的 |
| 标准 | ＋ 去协议后的 URL、域名+去尾路径 | **默认**，兼顾准确与召回 |
| 宽松 | ＋ 同域名下标题相似度 ≥ 阈值 | 默认阈值 0.92，可调 |

路径尾部清理：`/index.html`、`/index.htm`、`/index.php`、`/default.aspx`
视为等价于 `/`。

### 7.3 分组算法：并查集

三种键会产生**重叠**分组，需要传递闭包，不能简单分桶。
用 Union-Find 合并：同一条书签被多个键命中时，把所有相关组合并成一个组。

宽松档的标题相似度是 O(n²)，因此加保护：**单域名条目数 > 400 时跳过该域名的相似度比较**。

### 7.4 保留策略

重复组内保留**最早添加**的一条（`add_date` 最小）——最早收藏的通常是最初想保存的。
其余标记 `keep=False`。

**去重是可逆标记，不是删除。** 用户可：
- 勾选"隐藏重复项"只看保留结果
- 右键单独切换保留/剔除
- 导出时选择"只导出保留项"或"全部"

### 14.4 两个关键合规点

**① PyInstaller 的 GPL 例外条款**

PyInstaller 自身是 GPLv2，但带有明确的例外：

> 允许使用 PyInstaller 打包**任意许可证**的应用程序（包括专有软件），
> 前提是不得修改 PyInstaller 自身源码。

结论：用它打包本项目**不会**导致项目被 GPL 传染。条件：
- 不修改 PyInstaller 源码
- 若分发时包含其二进制，提供源码获取途径

**② PySide6 / Qt 的 LGPL 义务**

Qt 提供 LGPLv3 / GPLv2 / GPLv3 三选一，本项目走 **LGPLv3**。
LGPLv3 下分发**闭源**应用需满足：

- 使用**动态链接**（PyInstaller 打包的 Qt DLL 满足此点）
- 随附 LGPLv3 全文与 Qt 版权声明
- **提供替换 Qt 库的途径** —— 实践中需说明用户可自行替换 Qt DLL，
  或在分发包中提供 `Qt*.dll`
- 若修改了 Qt 源码，修改部分必须开源

> 若希望彻底规避 LGPL 义务，可选方案：改用商业 Qt 授权，或换用
> MIT/BSD 许可的 GUI 框架（如 Dear ImGui + pyimgui、或 wxPython）。
> 这是架构决策，需权衡开发效率与合规成本。

### 14.6 杀软误报

PyInstaller 单文件（自解压）是杀软误报高发区。缓解措施：

| 方案 | 效果 | 成本 |
|------|------|------|
| 改用 `--onedir` 目录分发 | 误报率显著下降 | 分发从 1 个文件变成 1 个文件夹 |
| 代码签名证书 | 基本消除 | 需购买（数百至数千元/年） |
| README 说明 + 提供 SHA256 | 有限 | 几乎为零 |

建议：先用 `--onedir` 分发；若确需单文件且用户量上去，再考虑签名。
